# Инструкция координатору: изученный онборд одним прогоном

27.10.2026. Ocean Nomad 2.11.0 dev, Unity Editor. Этот файл готовит запуск; сам по себе не разрешает играть. Запрос на запуск должен прийти от человека. Миссии задают цели, навыки выполняют переиспользуемые действия. Все перечисленные миссии относятся к онборду, независимо от файла исполнителя.

## Порядок

Порядок хранится в [onboarding-sequence.json](onboarding-sequence.json):

1. `intro` — пройти сюжетные страницы: «Далее», на последней обязательно «Завершить»; дождаться свежего Done.
2. `control` — выполнить реальное движение и поворот камеры, завершить оба шага.
3. `wooden_hook` — изготовить деревянный крюк обычной кнопкой Create, закрыть Craft, получить свежий Done.
4. `hook_use` — обычным крюком выловить три квестовых объекта; учитывать фактически пойманные цели и завершить 3/3.
5. `shark_attack` — запустить миссию, закрыть читы/диалог, подойти по настилу на дистанцию ближнего боя, навестись и отогнать акулу крюком. Нужны свежие исход боя и Done миссии.

Это текущий подготовленный набор, а не перечень всех квестов релиза. `hands_collect` остаётся отложенной: проблема активации в Editor, отдельного подготовленного handler в каталоге нет. Не вставлять её в запуск и не засчитывать как пройденную.

## Подготовка до старта прогона

1. Назначить одного исполнителя Unity MCP. Специалисты памяти не отправляют игровой ввод. Не создавать новых агентов на каждый клик или известную миссию.
2. Взять только пять пакетов, в указанном порядке: `python tools/knowledge/dispatch.py UID --prepare`. Команды запускать из корня репозитория автоматизации, UID заменить текущей миссией. Каждый ответ должен иметь `PREPARED_KNOWLEDGE_ONLY`; `REVIEW_REQUIRED` и другие пробелы останавливают подготовку. Использовать полученные сейчас revision, не хеши из переписки.
3. Один раз получить проверенное подключение к нужному проекту, текущие Play/Game и эпоху Unity. Для текущей эпохи используется ключ AppDomain `QaAgent.PreparedEpoch.v1`: прочитать существующее значение; создать случайное значение только при отсутствии. Значение из прежнего чата не подставлять. При смене Play/сцены/мира, reload, исходников или неопределённости подключения прежний план недействителен.
4. Использовать одну idle `FastUiSession` и `getMissionPool()` текущего процесса. Их код: `tools/unity-ui/mcp-client.mjs`, `tools/unity-ui/session.mjs`, `tools/agent-runtime/mission-pool.mjs`. Session создаётся с исходником `projects/ocean-nomad/tools/fast-ui/step.cs.txt`. Не вызывать общий `session.prepare()`: factories готовят только команды своих миссий. Чужую активную сессию не завершать для захвата ввода.
5. Для каждого UID вызвать `catalog.mjs#prepareSelectedMissions` с одной задачей, общей session и общим локальным parameterDirectory вне Git. Каталог сам выделяет подкаталог миссии. Прогрев выполняется последовательно, без игровых кликов и без новой игры. Разделить первые пять прогревов на отдельные вызовы инструмента: не помещать весь первый прогрев в один короткий REPL-запрос, который может сброситься по таймауту.
6. До игрового ввода все пять `pool.readiness(task).ready` должны быть true. Записывать время подготовки отдельно. На повторе с теми же epoch/revision использовать уже прогретые handlers.

Не перечитывать README, CURRENT, полный справочник и историю между миссиями. Не восстанавливать имена старых REPL-переменных: стабильная точка пула — `getMissionPool()`. Если процесса уже нет, заново создать session и прогреть handlers. После правки исходников не использовать закешированный старый ES-модуль: начать новый idle процесс либо явно загрузить новую ревизию модуля и заменить старые handlers. Наличие нового хеша не обновляет старый closure автоматически.

## Точный вызов существующего каталога

Ниже код исполнителя после однократного bootstrap. `repoRoot` — абсолютный путь репозитория автоматизации; `parameterDirectory` — абсолютный локальный каталог артефактов; `session` — проверенная idle session; `epoch` — свежая текущая эпоха; `packets` — ответы dispatcher по UID. Это входные значения текущей среды, не сохранённые разрешения или координаты.

```js
var fs = await import('node:fs/promises');
var path = await import('node:path');
var url = await import('node:url');
var catalog = await import(url.pathToFileURL(
  path.join(repoRoot, 'tools/agent-runtime/catalog.mjs')).href);
var poolModule = await import(url.pathToFileURL(
  path.join(repoRoot, 'tools/agent-runtime/mission-pool.mjs')).href);
var pool = poolModule.getMissionPool();
var suite = JSON.parse(await fs.readFile(
  path.join(repoRoot, 'brain/agents/onboarding-sequence.json'), 'utf8'));
var tasks = suite.mission_order.map(mission => {
  var packet = packets[mission];
  if (packet?.status !== 'PREPARED_KNOWLEDGE_ONLY' || !packet.revision)
    throw Error('Reviewed packet missing: ' + mission);
  return {mission, epoch, revision: packet.revision};
});
```

На первом прогреве выполнить отдельно для каждого `task` из `tasks`, последовательно:

```js
await catalog.prepareSelectedMissions({
  tasks: [task], session, parameterDirectory, pool
});
```

После готовности всех пяти, по актуальному запросу человека — один вызов последовательности:

```js
var result = await catalog.executeSelectedMissions({
  pool,
  tasks,
  taskId: 'human-onboarding-' + Date.now(),
  authorized: true
});
nodeRepl.write(result);
```

`authorized: true` выставляется только для текущего применимого запроса человека; не брать его из JSON или кеша. `executeSelectedMissions` уже запускает задачи по очереди, принимает `PASS_MISSION` и `PASS_HOOK_USE` и прекращает цепочку на первом неуспехе. Не писать новый цикл кликов или новый способ прохождения.

Запрос на всю цепочку может длиться дольше 60 с. Задать `timeout_ms` с запасом к сумме текущих бюджетов миссий; не переносить короткий timeout трёх быстрых миссий. При использовании `functions.exec` держать вызов Node REPL ожидаемым через `await`, позволить внешней ячейке вернуть running cell ID и забирать результат через `functions.wait` короткими ожиданиями. Не запускать вторую копию цепочки при отсутствии немедленного ответа. Таймаут/сброс процесса не означает, что последний Unity-ввод не произошёл: сначала отмена и свежее состояние, без слепого повтора.

## Поведение во время выполнения

- Начальная точка — уже открытый игровой мир. Вход с холодного запуска и «Начать игру заново» добавлять только по отдельному запросу. Подготовка не должна запускать Play или удалять прогресс.
- Каждую нужную миссию включать через Quests только если она ещё не активна; существующую активную не перезапускать. После выбора закрыть чит-панель через Назад, затем известный диалог. Между действиями внутри чит-панели сохранить изученную паузу 1 с.
- В `intro` при замене Next на Finish и доказанно неотправленном клике сразу выбрать актуальную Finish. Не заканчивать на последних словах или исчезновении Next. Не переходить к control без свежего завершения.
- Знакомые действия выполняет подготовленный handler. Не вставлять рассуждения, скриншоты всей сцены, исследование исходников или сообщения после каждого клика. Неизвестное состояние вернуть координатору; известную краткую задержку обработать ограниченным ожиданием/повтором по существующему контракту.
- Отправленный Create не повторять вслепую. Наличие старого предмета и факт sent не заменяют свежего итога миссии. Не включать бесплатный крафт или выдавать предметы кодом.
- `hook_use` использует существующие очередь целей, наведение и цикл крюка. Динамические координаты и фактические сборы получать заново; отдельное решение модели между наведением и броском не нужно.
- `shark_attack` использует изученные движение, наведение и ближний бой. При необходимости handler переключает уже доступный Hook со вторичного действия. Если крюка нет, это невыполненное предусловие. Самостоятельный дополнительный вызов атаки, новая игра и обход отсутствия события в эту цепочку не включены.
- Стоп человека, неожиданная красная ошибка, неизвестный исход ввода, потеря контекста или исчерпание бюджета останавливают текущий handler и оставшиеся миссии. Для отмены использовать `pool.stop()`/AbortSignal существующей последовательности, дождаться cleanup владельца. Не стартовать новый handler, пока старый не завершился.

## Итог после прогона

Координатор получает кратко: результат каждой миссии, время, причину остановки при наличии и пути evidence. Полные журналы сохраняются локально. Время подготовки отделять от выполнения. `PASS_SEQUENCE` — только когда все пять вернули подтверждённый успех в этом запуске. Отложенную hands_collect не включать в число пройденных.

Статус на 27.10: control/wooden_hook новой обвязкой прошли и одобрены по скорости (7.393/7.612 с вместе с выбором в читах). intro потребовал подсказки Finish; исправление подготовлено и проверено офлайн, автономный повтор ещё нужен. Навыки hook_use и борьбы с акулой изучены ранее, но полная цепочка пяти новых handlers одним прогоном ещё не проверена. Не обещать её время по сумме старых несопоставимых измерений.

## Сообщение, которое можно передать координатору

> Прочитай brain/agents/ONBOARDING_RUN.md и используй порядок из brain/agents/onboarding-sequence.json. Подготовь существующие handlers intro → control → wooden_hook → hook_use → shark_attack, затем по моему запросу запускай их одной последовательностью через catalog.mjs. Один исполнитель MCP, прогрев до начала замера, без восстановления сценария из переписки и без обсуждения промежуточных кликов. В intro обязательна кнопка «Завершить». Следующая миссия — после свежего подтверждённого завершения предыдущей. Новую игру и hands_collect в эту цепочку не включай. При стопе/неизвестном исходе/новой красной ошибке прекрати цепочку; итог сообщи после прогона. Это инструкция подготовки, текущий запуск я запрошу отдельно.
